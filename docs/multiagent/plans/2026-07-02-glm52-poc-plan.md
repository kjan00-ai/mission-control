## 0. 선행 게이트 — 데이터 거버넌스 (PoC 진입 전 필수 통과)

> ⚠️ 이 게이트를 통과하지 못하면 성능이 아무리 좋아도 PoC 자체를 시작하지 않는다.
> 보험·금융·개인정보 도메인이 섞인 대표님 사업 특성상 성능보다 우선하는 관문.

| # | 확인 항목 | 통과 기준 |
|---|---|---|
| G1 | GLM API로 나가는 데이터 경로 | 코드·기획서가 z.ai 서버로 전송됨을 명시 인지. **실고객 PII/보험/금융 데이터는 절대 미투입** |
| G2 | PoC 입력 데이터 | 전부 **합성/더미 데이터** 또는 공개 가능 코드만 사용 (실 프로젝트 스냅샷은 마스킹) |
| G3 | 학습 이용 여부 | z.ai 약관상 입력의 모델 학습 이용 여부 확인 → **opt-out 불가 시 hard-block** (대표님 결재로도 우회 불가) |
| G4 | 키/엔드포인트 격리 | GLM 키는 PoC 전용 발급, 대표님 운영 secret과 분리 (CLAUDE.md secret=DENY 규약 준수) |

**게이트 규칙 (L2 blocker `455aa785` 반영 — 승인 우회 차단)**:
- **hard-block (대표 결재로도 우회 불가)**: G1(실 PII/보험/금융 투입) 위반, **G3 학습 opt-out 불가** — *미확인이 아니라 "위반/불가"로 확정되면 PoC 자체 금지*. 승인으로 통과 못 함.
- **결재 게이트 (미확인 → 대표 결재 후 진행)**: G2·G4 등 절차적 항목의 *미확인* 상태만 해당.
- ⚠️ 기존 "하나라도 미확인 → 대표님 결재 후 진행" 문구는 hard-block까지 승인으로 우회시킬 소지 → 위와 같이 분리.

## 1.5. 평가 아키텍처 — L2 통합 (핵심)

### 현행 → 변경
- **현행 L2**: Codex(기술) ∥ Gemini(운영/UX) 2벤더. Claude는 생성자라 검증단 밖.
- **변경**: GLM이 생성자로 내려오면 **Claude가 중립 검증자로 L2에 합류** 가능 → 원본 §7 "코드검증 1위=Claude"와 정합. **L2 패널 = Codex ∥ Gemini ∥ Claude**.

### 성능지표 = L2-verified concordance
GLM 산출물이 **작업별 L2를 BLOCKER 없이 통과한 비율**이 곧 성능. 별도 점수 매기기 아님.
매 작업이 곧 평가 데이터 → 상시·전 프로젝트 축적. (근거: B사이클 [[b4-ready-verifier-budget-not-metric]] "검증=증거")

### 위험도 티어링 (대표님 확정 2026-07-02)
> Claude L2를 매 작업 태우면 GLM 도입의 비용절감 명분이 상쇄됨 → **기존 decision-policy T0~T3 재사용**으로 해소.

| 티어 | 대상 | L2 패널 | Claude |
|---|---|---|---|
| **T0/T1** | docs·routine CRUD·단순 페이지 | Codex ∥ Gemini | **샘플링**(N건당 1건) |
| **T2/T3** | auth·결제·마이그레이션·보안·개인정보·보험/금융 판단 | Codex ∥ Gemini ∥ **Claude** | **상시 필수** (단 L2가 놓치는 버그는 여전히 잔존 — 캘리브레이션으로 발견율 보증, "자동 담보" 아님. L2 imp `b5c38a35`) |

T2/T3 목록 = 원본 §6·§11 "GLM 단독금지 영역"과 일치. 새 분류체계 불필요 — 기존 위험분류기가 그대로 게이트.
**비용우위 가설 (L2 `4add829a` 반영 — 단언 아님, GO-1로 검증)**: "검증 토큰 < 생성 토큰이므로 (GLM 생성 + Claude 검증) < (Claude 단독 생성)"은 **PoC에서 실측·검증할 가설**이지 확정 결론이 아니다. 검증 비용·재시도 왕복·T0/T1 샘플링 비율을 실측해 **GO-1(총비용 ≤ Claude 40%)**로 판정하기 전에는 비용우위를 전제하지 않는다.

### 2층 평가 모델
| 층 | 주기 | 방법 | 답 |
|---|---|---|---|
| 캘리브레이션 | 프로젝트 온보딩 1회 | seeded-bug 정답셋 → **L2 패널(Claude 포함)이 GLM 오류를 잡는지** | "우리 L2가 GLM 실수를 거르나?" |
| 상시 운영지표 | 모든 작업·모든 프로젝트 | L2-verified concordance | "실전 GLM 쓸 만한가?" |

L2 concordance 단독으론 L2가 놓친 버그를 못 잡음 → seeded-bug가 그 눈금을 보증.

## 2. 테스트 과제 (원본 §12 기반 + 정답셋 보강)

각 과제는 **동일 입력을 4모델에 동일 프롬프트로** 투입한다. 프롬프트는 사전 고정(과제당 1개, 변형 금지).

### 과제 A — 프론트 구현 (최우선, 대표님 통증점)
- **입력**: 확정 디자인 시스템(컬러/폰트/버튼/카드 규칙) + 예시 스크린샷 + 페이지 요구사항 1건
- **요구 산출물**: Next.js 페이지 + Tailwind + 반응형 + 재사용 컴포넌트 + 더미데이터
- **정답셋**: mission-control의 기존 검증된 페이지 1개를 "기준 구현"으로 삼아 비교 기준선 확보

### 과제 B — 대량 CRUD/API 생성
- **입력**: DB 엔티티 3개 스펙 + 기존 코드베이스 패턴(라우트 규칙, 폴더 구조)
- **요구 산출물**: API 라우트 + CRUD 모듈 + 타입 + 테스트 초안
- **정답셋**: 기존 repo의 동종 모듈을 "골든 샘플"로 지정 → 패턴 준수도 대조

### 과제 C — 1차 코드검증
- **입력**: **의도적으로 버그 N개를 심은** 코드 + 테스트 실패 로그 + 변경 diff
- **요구 산출물**: 문제 원인 / 수정안 / 영향범위 / 테스트 명령 / 재발방지 체크리스트
- **정답셋**: 심은 버그 목록이 곧 정답 → **버그 발견률을 객관 측정 가능** (핵심 개선점)

> 과제 C의 "seeded bug" 방식이 원본 §12의 최대 공백(채점 순환논리)을 해소한다.
> 정답을 미리 알고 심으므로, AI가 AI를 채점하는 순환 없이 발견률을 숫자로 잰다.

## 3. 채점 rubric (고정 — PoC 시작 전 확정, 이후 불변)

> 원본 문서는 "상/중상/최상" 정성 등급뿐이라 변별력이 없었다. 아래를 **0~5점 정량**으로 대체.

### 공통 채점 축 (전 과제)
| 축 | 가중치 | 측정법 |
|---|---|---|
| 정확성 (요구 충족) | 30% | 요구항목 체크리스트 충족 개수 |
| 수정 왕복 횟수 | 20% | "동작하는 상태"까지 사람이 개입한 횟수 (적을수록↑) |
| 비용 | 20% | 과제 완료까지 총 토큰 비용 (USD) |
| 소요시간 | 15% | 최초투입~완료 wall-clock |
| 코드 품질 | 15% | 가독성·패턴준수·중복 (골든샘플 대조) |

### 과제별 특화 축
- **A(프론트)**: 디자인 일관성 / 여백·정렬 / 반응형 / 컴포넌트 재사용성 (각 0~5, 스크린샷 대조)
- **B(CRUD)**: 기존 패턴 준수율 / 타입 안전성 / 누락 엔드포인트 수
- **C(검증)**: **버그 발견률**(발견/심은수), **오탐률**(false positive), 보안 리스크 감지, 회귀위험 감지

### 채점자 (순환논리 차단)
1. **1차 정량**: 자동 측정(토큰·시간·테스트통과·seeded bug 발견수)은 스크립트/로그로 기계 집계
2. **2차 정성**: 디자인 일관성 등 주관 항목은 **고정 rubric에 따라 위임 채점** (대표님 확정 2026-07-02 = rubric 위임, 대표님 직접 채점 아님). 대표님은 rubric 확정·최종 Go/No-Go만 관여
3. **L2 concordance는 캘리브레이션 검증 대상**: seeded-bug 정답셋으로 L2 패널(Claude 포함)의 발견률을 재고, L2가 정답을 놓치면 → L2 신뢰 확보 전까지 상시지표로 승격 금지
4. GLM 자신에게 채점 위임 금지 (위임 시 순환) — L2 검증단(Codex∥Gemini∥Claude)이 채점 주체

## 5. Go / No-Go 판정 기준 (사전 고정)

GLM-5.2를 "3단계 대량구현 보조모델"로 **정식 편입(Go)**하는 조건:

| 조건 | 임계값 |
|---|---|
| GO-1 비용효율 | 동급 과제에서 GLM 총비용이 Claude 대비 **≤ 40%** (핵심 도입 명분) |
| GO-2 품질 하한 | 과제 A·B 정확성 평균이 Claude 기준선의 **≥ 80%** |
| GO-3 수정 왕복 | Claude 대비 수정 왕복 **≤ 1.5배** (증폭 효과가 재작업으로 상쇄되지 않을 것) |
| GO-4 검증 안전 | 과제 C에서 **critical 버그(인증/결제/보안) 미탐 = 즉시 실격** → 검증자로는 부적격 확정 |
| GO-5 L2 concordance | 캘리브레이션 통과 후, 초기 표본에서 T0/T1 작업 concordance **≥ 70%** (T2/T3는 Claude 상시 검증으로 위험을 낮추나 "자동 담보"는 아님 — 캘리브레이션 발견율이 그 잔존위험의 눈금. L2 imp `b5c38a35`) |

**판정 규칙**:
- GO-1·2·3·5 충족 → **대량구현 보조 Go** (원본 §13 3단계 배치 확정, 위험도 티어링으로 상시 편입)
- GO-4 실패 → GLM 검증자 역할 영구 배제. **단 GLM은 생성자이므로 검증은 Claude가 맡음 → 무관** (오히려 티어링 설계가 이를 이미 보장)
- GO-1 미달 → 비용 명분 소멸 → **도입 보류** (성능만으론 Claude 교체 이유 없음)
- **캘리브레이션(seeded-bug) 실패 시** → L2가 GLM 오류를 못 거른다는 뜻 → concordance 지표 신뢰 불가 → L2 패널 보정(Claude 비중↑) 후 재측정

## 7. 리스크 / 주의

- **벤치마크 과신 금지**: 본 PoC 수치만 신뢰, 원본 문서의 공급사 벤치마크(Terminal-Bench 버전 불일치 등)는 참고만
- **엔드포인트 호환성 불확실**: §9의 "Anthropic 호환" 주장이 실제 Claude Code와 매끄럽게 붙지 않을 수 있음 → 2단계에서 조기 검증, 실패 시 Cline 대안
  - **대안 사전조사 필수 (L2 imp `9e30f000` 반영)**: Cline/Kilo Code 대안을 실패 시 즉흥 채택하지 않는다. 2단계 착수 전 각 대안의 **① 도입 여부(신규 설치/기존 보유) ② 비용 ③ GLM 연결 방식·Claude Code 대체 기능 커버리지**를 표로 사전 확정. 조사 미완 시 §8 미결정에 편입해 대표님 결재.
- **비결정성**: 단발 실행 판단 금지, 반복 중앙값
- **범위 팽창 방지**: 기획/최종설계는 PoC 제외(문서 결론 이미 명확), 3·4·5단계에만 집중
- **에이전트 SDK 무관**: 본 PoC는 base URL 교체 방식 → 대표님 "에이전트 SDK 도입 금지" 규약과 무관하나, 추가 오케스트레이션 필요 시 대표님 결재 게이트
- **shared 인프라 변경 리스크**: L2 패널·decision-policy는 전 프로젝트 영향 T2/T3 → 반드시 WSL canonical 단일편집 + `maia-deploy` 동기(hand-cp 금지) + 드리프트 확인.
  - **롤백 (L2 imp `abac6594` 반영 — 정책 json 되돌림만으론 불충분)**: ① `decision-policy.json` = 값 되돌림 ② **`l2-loop.js` 코드 변경 = `git revert <sha>`** (ai-bootstrap repo) ③ `maia-deploy` **부분 실패/드리프트** = `maia-deploy --check` + `maia-health.js` md5 대조로 탐지 후 재동기 ④ 실행중 프로젝트의 **정책 버전 경합** = 전파를 Go 후로 이연(§적용범위)해 원천 회피.
