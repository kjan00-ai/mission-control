## 0. 문제 정의 (왜 C6인가)

C5(Autonomy Overhaul)는 "위험임계점에서만 인간 게이트"를 도입했다. 그 게이트의 실체 = **T2 `ask` 모달**. 그러나 운영에서 드러난 근본 결함(대표 지적 2026-06-13):

1. **모달 결재는 검토가 아니다.** 대표가 모달 한 건을 볼 때, 진행 중인 코딩 전체 맥락을 실시간 검토할 수 없다 → 사실상 **무조건 Yes** → 안전 기여 0, 흐름만 끊김. 안전의 *착시*.
2. **T0~T3 계층은 목적이 아니라 부산물.** "자율진행 + 무모달"을 구현하려다 나온 트리아지 도구일 뿐. 진짜 목적은 **(a) 리스크 작업의 사전 예방, (b) 리스크 발생 시 사후 대처·해결**.
3. **인간 결정도 원래는 MAIA가 먼저 결정·실행한 뒤 결과로 검증**해야 한다. 대표는 그 **결과만 보고 판단**하는 것이 맞다.

→ 결론: **"누가 승인하나"(결재)** 축을 폐기하고, **"어떻게 검증·복구하나"** 축으로 안전을 재구성한다.

### 0.1 보존할 것 (C5 자산)
Decision Gate(빠른 분류), L2 엔진(`l2-loop.js`), Auto-L2(Stop 훅 사후 안전망), 실시간 알림(Telegram), 회귀테스트 자산(risk-classify 190케이스), audit 로그. **C6는 이 위에 얹는다 — 폐기가 아니라 재배선.**

## 1. 재설계 원칙

> **안전 = 가역성(Reversibility) × 검증(Verification) × 복구(Recovery). 결재(Approval)는 안전 함수에서 제외한다.**

- **가역성이 1차 축.** 되돌릴 수 있으면 "실행 후 검증"이 성립한다. 그래서 C6의 핵심 엔지니어링은 **비가역 작업의 가역화**다(§3).
- **검증은 인간이 아니라 MAIA L2가 한다.** 사전(예방) + 사후(탐지)를 요소요소에 배치. L2도 틀리므로(§5.3) 단일 게이트로 신뢰하지 않고 다층(분류기+L2+테스트+audit+롤백).
- **인간은 결과를 비동기 배치로 검토한다.** 모달 스트림 → **결과 다이제스트**(무엇을 결정·실행했고 / L2 판정 / 롤백 커맨드). veto·rollback만.

> **★ 정책 축 구조(v0.3): 노출 축 2개 — 실행 축 E(§1.1) × 검증 축 V(§1.2).** 가역성 R(§1.0)·위험·작업난이도 W는 *내부 입력*(분류기가 단일 레코드로 산출). E = "어떻게 실행/게이트하나"(can/how it runs), V = "얼마나 리뷰하나"(how much review).

### 1.0 가역성 Taxonomy — 실행 축 E의 1차 입력 (L2 검토로 추가된 토대)

C6의 모든 자율 판단은 이 분류 위에서만 성립한다. **"가역화 가능"의 경계를 엄격히 정의하지 않으면 T3 자율화가 안전모델을 과장한다**(codex). 따라서 가역화 레이어(§2.2)보다 **이 판정기가 먼저** 있어야 한다.

> ★ **R은 실행을 직접 규정하지 않는다(L2 round3 codex BLOCKER).** R은 §1.1 실행 축 E의 *입력*이다. 아래 "→ E" 열은 (R, 위험) 룩업의 **결과 예시**일 뿐, 실행 통제의 SSOT는 §1.1 E lookup이다(이중 SSOT 방지).

| 가역 등급 | 정의 | → 실행 등급 E (§1.1 룩업, 위험 따라) |
|---|---|---|
| **R0 완전가역** | 스냅샷/git/트랜잭션으로 100% 원복 | 저위험 **E0**(사후검증) / 고위험 **E1**(사전가드) |
| **R1 시간제한 가역** | 일정 창(window) 안에서만 취소 가능, 창 종료 후 비가역 | **E2**(지연+veto, timeout 자동실행) |
| **R2 부분복구** | 되돌리되 잔여 side-effect/정합성 손실 가능(DB down, 패키지 설치) | 복구보장 시 **E1/E2** / 정합성손실 크면 분류기가 **R3 판정→E3** |
| **R3 비가역(사회적/물리적)** | 디지털 상태는 몰라도 **사회적·물리적 결과는 복구 불가** — 발송된 메시지의 평판, 과금 API, 제3자가 이미 소비/캡처/전파한 상태, secret 노출, 시간·자산 손실 | **E3**(지연+veto, timeout 차단) 또는 **DENY** |
| **DENY** | 절대 금지 | **DENY**(즉시 차단) |

★ **핵심 원칙(both)**: **"가역화 불가(R3) = E3(지연큐+인간 비동기 veto) 또는 DENY"**. 디지털 가역성과 사회적 가역성은 다르다 — `git revert`는 되지만 *이미 읽힌 메일·트윗·결제·유출된 키*는 못 되돌린다. **L2 단독 게이트 금지**는 E3/DENY에서 강제된다.

### 1.1 실행 축 E (R·T 통합) — 권한/위험을 단일 실행 게이트로 (편입 v0.3, 2026-06-16)

> 구 Decision Gate T0~T3(권한/위험)와 §1.0 가역성 R을 **단일 실행 축 E**로 통합. T(위험)·R(가역성)은 둘 다 "이 작업을 어떻게 실행/게이트하나"를 묻는 상관 입력이라 별도 0~3 사다리 2개는 인지부하 → **입력은 보존, 출력(실행 게이트)만 통합.** 상세 SSOT = [[2026-06-16-rt-execution-axis-merge-design]].

**E = 실행 마찰(execution friction) ladder** (R에 1:1 매핑 아님):
| E등급 | 실행 통제(requiredControls) | timeout 기본동작 |
|---|---|---|
| **E0** | 자율 실행 + 사후검증 | — (즉시) |
| **E1** | 자율 + **사전가드(스냅샷·드라이런·사전 L2)** | — (구 T2 처리 인코딩) |
| **E2** | 지연 실행 + veto창 | **자동 실행**(회수 가역, R1) |
| **E3** | 지연 실행 + veto창 | **자동 차단**(비가역 잔여, R3) |
| **DENY** | 즉시 차단(absorbing) | — (force push·secret 등) |

**(R 가역성, 위험) → E 2D 룩업**(단일값 결정함수, `decision-policy.json` 데이터):
| R \ 위험 | 저위험 | 고위험 | always-deny |
|---|---|---|---|
| R0 | E0 | **E1** | DENY |
| R1 | E2 | E2 | DENY |
| R2(복구보장) | E1 | E2 | DENY |
| R3 | E3 | E3 | DENY |
R2-R3 경계는 *가역성 분류기*가 흡수(복구보장=R2, 정합성손실=R3). 외부발신처럼 발신=비가역이면 E3.

**출력 = 구조화 레코드** `policyClassification {reversibility, riskFlags, executionLevel(E), requiredControls, verificationDepth(V|not_applicable), denyReason, escalatedBy, …}` — 단일 분류기 산출, 에이전트는 **복종만**(계산 안 함). E축 **자동 하한 게이트**로 R 허위신고 방어. 분류기 실패 시 **안전폴백 (DENY/E3, V3)**.

**구 T0~T3 마이그레이션**(deny-reason 기준, T-label 아님): T0/T1→E0/E1 / T2→E1(사전L2+스냅샷) 또는 룩업 / T3 `r3_residual`→E3 / `hard_deny`→DENY. **golden fixture + CI 회귀가드**(구 DENY가 E0~E2로, hard_deny가 E2/E3로 내려가면 Hard Block).

핵심 변화: **권한/위험(T)·가역성(R)이 별도 노출 축 → 단일 실행 축 E.** ask 모달 폐지, T3 deny는 가역화(E1~E3) 또는 hard_deny(DENY)로 분기. *실행 허가는 E가, 리뷰 깊이는 V가* — 혼동 분리.

### 1.2 검증 깊이 차원 (V) — 안전함수의 "검증"을 깊이로 정량화 (편입 2026-06-16)

> §1의 안전 = 가역성(R) × **검증(V)** × 복구. 그 "검증"이 *얼마나 깊어야 하나*를 작업 난이도로 정량화한다. 상세 SSOT = [[2026-06-16-verification-depth-axis-and-resilience-spec]] (dev-case 2026-06-16 S-2 확장, L2 BLOCKER3 반영).

- **작업 클래스 W0(기계적)~W3(설계 결정) → 검증 깊이 V0(가드만)~V3(풀 L2)** floor+escalator 매핑. dev-case 실측(단순작업에 풀파이프라인 일률적용=시간낭비)을 구조적으로 교정.
- ★ **V는 "얼마나 리뷰하나"일 뿐 "실행 가능 여부"가 아니다**(L2 codex BLOCKER). 실행 게이트는 **실행 축 E(§1.1)** 가 한다. V3라도 R3/E3 작업의 실행은 지연큐/veto/DENY로 따로 막힌다.
- **2축 모델(상관 있는 분리 차원)**: **E(§1.1)가 실행을 게이트(can/how it runs) → V가 리뷰 깊이를 정함(how much review).** 위험(riskFlags)은 두 축의 공통 입력(E·V 양쪽 상향), audit에 `escalatedBy`로 원인 태깅.
- 고위험은 작업이 단순(W0)해도 V 하한을 끌어올린다. 자기선언 하향 도덕적 해이는 사후 audit이 못 막으므로(audit≠사전게이트) **자동 하한 게이트**로 사전 방어 — diff escalator **+ task-intent/요청출처 classifier**(작은 diff·큰 의미 설계변경 방어, L2 round2). 분류기는 AST 배제·단순 정규식 MVP로 범위 제한.

## 2. 컴포넌트 (무엇을 만드나)

### 2.1 사전 검증 게이트 (E1+ 예방) — `[기획결정: 입도·지연]`
- E1 이상(구 T2, 사전가드 필요) 작업은 **인간 모달 대신 사전 L2/룰 검증** 후 자율 진행.
- ★ 난제: 모든 E1+ *도구호출*마다 풀 L2(분 단위)는 불가. → **입도를 '도구호출'이 아니라 '결정/산출물' 단위로.** 빠른 룰 판정(분류기)은 도구호출마다, 무거운 L2는 결정 지점에만.
- `[기획결정]` 사전 L2의 트리거 입도(파일군/커밋/PR/세션 phase 중 무엇), 경량 1차 체크(룰/소형모델) vs 풀 L2 분기 기준, 캐싱.
- ★ `[기획결정]` **검증기 메커니즘**: 현재 L2는 외부 CLI(`codex`/`gemini`/`hermes`)에 셸아웃. → **네이티브 Claude 서브에이전트(Agent/Workflow 툴)로 전환** 검토 — 외부 CLI 의존·인증·과금 제거 + 단일 벤더로 단순화 + 병렬·구조화 출력 용이. 외부 CLI는 opt-in 폴백. 이 전환은 C6 검증 설계의 일부이자 §6(C7 공개 패키징)의 최대 전제다.
- ★ **입도 난제 해소(편입 2026-06-16)**: 위 입도/경량분기 `[기획결정]`은 **검증 깊이 축(§1.2)** 으로 답한다 — 입도=결정/산출물 단위, 깊이=W→V floor+escalator, 사전 경량체크=**자동 하한 게이트**(diff 휴리스틱 분류기). 풀 L2는 V3 결정지점에만, 빠른 룰은 도구호출마다. 상세·L2반영 [[2026-06-16-verification-depth-axis-and-resilience-spec]].

### 2.2 가역화 레이어 (E3 잔여를 낮은 실행마찰로 재분류) — `[기획결정: 범위·우선순위]`
> ★ **L2 round3 codex**: 가역화의 목표는 "E0~E1 완전자율"이 아니다 — 가역화 결과는 R1이면 **E2**, R2 고위험이면 **E2**, R3 잔여면 **E3**일 수 있다. 각 가역화 후보는 `resulting R`뿐 아니라 **`resulting E (§1.1 룩업)`** 을 명시한다. E2의 지연/veto를 누락하지 말 것.
"실행 후 결과검토"가 성립하려면 되돌릴 수 있어야 한다. 비가역 작업별 가역화:
| 비가역 작업 | 가역화 방식(후보) |
|---|---|
| 작업 | 가역화 방식(후보) | 가역등급(§1.0) |
| main/master 직접 push | **브랜치 push + 자동 PR**(머지 전 검토창; 머지가 진짜 게이트) | R0 (PR 머지 전) |
| 파일/데이터 삭제 | 소프트삭제·`.trash`·보관 후 TTL 정리 | R0~R1 |
| DB migration | up/down 쌍 + 스냅샷 + 드라이런 우선 | **R2**(down 100% 보장 불가, 정합성) |
| 패키지 설치 | lockfile diff 스냅샷 + 1커맨드 롤백 | **R2**(side-effect) |
| 외부 발신(메일/SNS/텔레/SMS) | **지연 발송 + 회수창**(N분 hold) | **R1→R3**: ★발송 *전* 취소일 뿐 발송 *후*는 비가역 |
- ★ **L2 교정(both)**: 외부 발신은 "발송 후 가역"이 아니라 **"지연큐 동안만 자율, 실제 발신 후 비가역"**. SMS/외부메일은 회수 매체조차 없음 → R3로 모델링, 발신 시점에 인간 비동기 veto window 또는 별도 정책.
- `[기획결정]` 가역화 우선순위(어느 E3부터), **R3 비가역 잔여 목록의 명시적 정의**(진짜 인간/지연큐 대상), PR 자동화가 기존 c4b/relay와 어떻게 엮이나.

### 2.3 결과 다이제스트 (인간 인터페이스) — `[기획결정: 형태·채널]`
모달 스트림을 대체하는 **비동기 배치 검토 뷰**: MAIA가 결정·실행한 것 + L2 판정 + **롤백 커맨드**를 묶어 제시. 대표는 보고 veto/rollback.
- ★ **L2 경고(both): "그냥 요약"이면 고무도장을 사후로 옮긴 것뿐.** 다이제스트가 모달보다 실효를 가지려면:
  - 각 항목 헤더에 **(E 실행등급, V 검증깊이)** 를 최상단 노출 + `escalatedBy`(어느 입력 R·W·위험 때문에 격상됐나) · `denyReason` · **L2 근거(Why)** · diff · 영향 범위 · 롤백 가능 여부 · `requiredControls` · (E2)`vetoDeadline/scheduledExecutionAt` · 가역등급 R(설명용) 순. — 인간 인지부하 내 축약 (L2 round3 both: R 중심→E/V 중심 재정렬).
  - **"전부 검토"가 아니라 "샘플링 + 고위험 집중 + 이상징후 알림"** (전수검토는 다시 고무도장).
  - **단 한 번의 veto로 즉시 전체 롤백되는 강력한 파이프라인**이 전제.
- `[기획결정]` 채널(대시보드 뷰 / 텔레그램 다이제스트 / 위키 리포트 / 셋 혼합), 주기(세션종료/일배치/임계초과 즉시), 롤백 UX(1클릭/커맨드), 어느 등급까지 다이제스트에 올릴지.

### 2.4 사후 탐지·복구 강화 — `[기획결정]`
- Auto-L2(사후) 유지하되 **BLOCKER 발견 시 자동 롤백 후보 제시**까지 확장.
- ★ 하네스 제약: Stop 훅은 비블로킹 → 사후 L2는 *안전망*이지 게이트 아님(기존 기록). 그래서 **사전 게이트(2.1)와 가역화(2.2)가 1차 방어**, 사후는 보완.

### 2.5 오케스트레이션 복원력 + 검증 효율 (S-1/S-3/S-4) — dev-case 2026-06-16 편입

## 3. 난제 (정직하게 — 기획단계 핵심 의제)

1. **★ 사회적/물리적 비가역성(both, 최우선).** "디지털 상태는 가역적이어도 사회적 상태는 비가역적." 발송 메시지의 평판, 과금 API, 제3자가 이미 소비/캡처/전파한 상태, secret 노출, 시간·자산 손실은 스냅샷·롤백으로 못 되돌린다. → **R3는 L2 단독 게이트 금지**(§1.0): 지연큐 + 인간 비동기 veto window 또는 DENY. C6의 안전 모델이 과장되지 않으려면 이 경계가 엄격해야 한다.
2. **가역화가 진짜 일감.** C6의 성패는 §1.0 판정기 + §2.2에 달림. 가역화 못 하는 R3는 결국 지연큐/인간에게 남고, 거기서 모델이 깨지면 안 됨.
3. **사전 L2 지연 vs 입도.** 도구호출 단위 풀 L2 불가 → 결정 단위 + 경량 1차 체크. 입도 설계가 핵심.
4. **L2도 틀린다 — 가역영역=수용, 비가역영역=치명(both).** 가역(R0~R2) 작업에선 L2 오탐도 되돌릴 수 있어 수용 가능(audit·회귀테스트로 학습). **그러나 R3에서 L2 false-negative=복구불능 사고** → R3는 L2에 전권 금지. 이번 C5-2a/C5-0c 병합에서 codex·gemini가 *서로 다른 걸 놓침*(교차보완)·false-blocker 실측 = L2 단독신뢰 금지의 증거.
5. **신뢰 부트스트랩을 C6-0부터(gemini).** "MAIA가 먼저 결정"의 전제 = MAIA 판정 신뢰도 계측. **과도기 단계 필수: L2 판단 vs 인간 판단을 대조해 성적표를 매기는** audit. 신뢰 임계 도달 전엔 보수적. 이건 마지막이 아니라 **C6-0부터 병행하는 데이터수집 과제**.
6. **하네스 제약.** 사후 훅 비블로킹. 사전 동기 L2는 PreToolUse(느림) 또는 에이전트 행동규약 의존. 기술적 한계 내 설계 필요.

## 6. 후속 방향 — C7: MAIA 공개 패키징 (Plugin) `[방향 메모, C6 이후]`

> 대표 문의(2026-06-13): C6 구현 후 MAIA를 skill로, public 제공 가능한가? → **bare skill은 불가**(스킬은 게이트 훅을 settings.json에 등록 못 함), **plugin은 가능**(플러그인은 훅+스킬+커맨드+스크립트를 번들, 활성화 시 PreToolUse/Stop 훅 자동 발동). public 경로 = 플러그인 마켓플레이스(Anthropic 공식 curated / community 제출 / 사설 Git). (claude-code-guide 확인, 2026-06-13.)

- **올바른 배포물 = plugin**(skill 아님). 게이트의 본질이 훅이라 plugin만 강제 가능.
- **진짜 일감 = 패키징이 아니라 환경 decoupling**:
  | 결합 | public화 |
  |---|---|
  | L2가 codex/gemini/hermes CLI 셸아웃 | **네이티브 서브에이전트로 전환**(§2.1) — 외부 바이너리 번들 불가·인증·과금 제거. 최대 관문 |
  | `~/.ai-bootstrap`·WSL/Windows 브리지 하드코딩 | config 기반·크로스플랫폼 |
  | Obsidian 위키 적재 / Telegram 알림 | 출력·알림 채널 추상화 |
  | 정책이 워크플로 전용(feat/* 자율·trustedPushMainProjects) | 안전 기본값 + override 파일 |
- **caveat(공개 거버넌스 도구)**: 훅 fail-open(타임아웃 시 통과 → 조용한 무력화) · Stop 훅 연속거부 캡(auto=안전망≠게이트 재확인) · 훅 무샌드박스(설치=임의코드 신뢰) · 비용/인증.
- **C6와의 관계**: C6의 "검증 우선" 모델 = 그 자체로 범용 가치 제안("자율 코딩 거버넌스"). C6가 C7을 *자동으로* 가능케 하진 않지만, **L2 네이티브 전환(§2.1)을 C6에서 처리하면 C7의 최대 전제가 해소**된다.

### 6.1 협조형(cooperative) vs 강제형(enforced) 모델 — 무결성 구분
> 대표 문의(2026-06-13): plugin 설치 유저가 코드·설정을 임의 변경 가능한가? → **자기설치 plugin은 변경 가능**. (claude-code-guide 확인.)

- **자기설치 public plugin = 협조형**: 설치 시 `~/.claude/plugins/cache/`로 복사되는 **유저 소유 평범한 파일**. 서명·해시·읽기전용 **무결성 검증 없음** → 유저가 스크립트·정책 JSON 편집, `/plugin disable`·uninstall로 훅 끄기 자유. 마켓 SHA 핀은 *업스트림* 변조만 막고 로컬 변조는 못 막음. = "감시받는 자가 감시자를 끌 수 있음."
- **강제형 = 관리(엔터프라이즈) 설정만**: 관리자가 MDM/`managed-settings.json`/admin 콘솔로 `enabledPlugins`·`strictKnownMarketplaces`·hooks를 **managed scope**로 잠그면 유저 override·편집·disable **불가**(`--plugin-dir`로도 못 뚫음).
- **MAIA 함의**: public 배포는 **협조형 자기거버넌스**(유저가 *자기 에이전트를 안전하게* 하려 스스로 켜는 가드레일 — C6 철학과 합치, '변조 가능'은 이 용도엔 결함 아님). "악의/부주의한 개발자·에이전트가 못 뚫게"가 목표면 → 관리설정 엔터프라이즈 배포(별도 제품군).

### 6.2 게이트 자기보호 (gate self-protection) — `[기획결정, C6에서 선반영 권장]`
- ★ **현재 구멍**: `~/.ai-bootstrap`(정책·분류기·훅) 편집이 T1(자율)이라 **에이전트가 자기 게이트 설정을 스스로 고칠 수** 있음. "감시자가 자기 규칙을 바꾸는" 자기참조 취약점.
- **수정**: 게이트 자체 구성요소(`decision-policy.json`·`risk-classify.js`·`~/.claude/hooks/*`·settings.json hook 등록부) 수정 = **DENY 또는 managed-only**로 못박기. 분류기 highRiskPaths/denylist에 게이트 SSOT 경로 추가.
- C6/C7 양쪽 전제(강제형이든 협조형이든 게이트가 자기 무결성을 못 지키면 의미 약화). C6 구현 시 선반영 권장.

### 6.3 비즈니스 모델 방향 — SaaS 유료화 `[방향 메모]`
> 대표 문의(2026-06-13): 무료(서브에이전트2·T2모달·T3거부)/유료(서브에이전트7·자율) 식 티어 가능? → **가능하나 게이트는 로컬 플래그가 아니라 *서버*에 둬야 함.** (claude-code-guide 확인: Claude Code 네이티브 결제·라이선스 *없음*, 마켓 무료전용.)

- **강제력 통로 = 인증 붙은 원격 MCP 서버**(HTTP) — 티어별 기능·쿼터를 *서버측*에서 게이트, 유저가 못 고침. 로컬 plugin 플래그/HTTP훅은 편집·제거 가능이라 paywall엔 부적합.
- ★ **핵심 통찰: "제약"은 과금 못 함, "서버 역량"을 과금함.** 게이트는 *보호*이지 withhold할 기능이 아님 — 무료 유저가 "모달 귀찮다"면 plugin을 지워 **게이트 0 = 완전자율**로 감. "덜 귀찮게"는 못 팖. → **자율을 잠그지 말고, 자율을 떠받치는 *서버측 L2 검증 역량*을 티어로 판다**(자율=검증강도로 *획득*, C6 철학 일치).
- **티어 재설계(예)**: 무료=2-관점 얕은 검증/T2 인간 체크포인트 유지 · 유료=7-관점 심층 적대검증(서버 실행·과금)/그 검증이 받쳐줘 자율진행 + 호스팅 다이제스트·팀 감사. "서브에이전트 N"은 *로컬 spawn 수*가 아니라 **서버가 돌리는 검증 관점/오케스트레이션 수**로 정의해야 과금·강제됨.
- **아키텍처**: 얇은 무료 plugin(훅/스킬) ──API키──▶ 대표 SaaS 백엔드(인증 MCP: 구독검증·쿼터·L2 오케스트레이션을 *서버에서* 실행). 과금 대상 = 백엔드 컴퓨트, plugin 파일 아님.
- **caveat**: 결제 인프라 BYO(Stripe+라이선스 서버) / 배포는 공식·커뮤니티 마켓(무료전용) 아닌 **사설·직접설치** / 결정마다 서버왕복 latency → 입도 설계(§2.1) / **ToS: Claude 감싼 유료 제공의 Anthropic 약관 제약 = 문서 미명시 → 상용화 전 Anthropic 확인 필수.**

- `[방향 메모]` §6 전체 지금 구현 대상 아님 — C6 완료 후 검토(단 §6.2 게이트 자기보호는 C6에서 선반영 권장). 본 절은 방향 보존용.
