# spec — `git clean` 게이트 반전 (열거 → 면제)

- 날짜: 2026-09-07
- 상태: **v0.5 — L2 4차 합의 6건 반영(수치 정합·주장 정정·마찰 고지). 검증 통과 · 대표 판정 대기**
- 배경: [git clean 등급 분리 spec](./2026-09-07-git-clean-t2-separation-spec.md) §7 — **실사고 발생분**
- 하네스: `~/p1c/candidates/clean-requireforce/`
- L2: 4사이클 × round 1~3 (claude ∥ gemini). 4차는 `evidenceEligible=true` — **합의 6건 전건 반영**, 미합의 2건은 대표 판정(§5). 3차는 `evidenceEligible=false`(round 1 parser fail) 라 자동신뢰 자격 없음 — 근거는 실측이다

> ⚠️ **v0.1 은 폐기됐다.** "우회 형태를 열거해 막는다"는 접근이 L2 에서 세 방향으로 뚫렸고, 그중 하나는 **위협모델 자체가 틀렸음**을 보였다. v0.2 는 열거를 버리고 **안전한 형태만 면제**한다.

## 1. 실사고

```
git -c clean.requireForce=false clean -d      →  T1 (자율 실행)
```

격리 repo 실동작 확증:

```
before: junk.txt junkdir
$ git -c clean.requireForce=false clean -d -q      → 게이트 T1 통과
after :                                             ← 둘 다 삭제
```

발견 보고 **직후 이 우회가 실제로 실행되어** 작업 산출물(당시 미추적이던 spec 문서)을 삭제했다. 그때 "코퍼스 실사용 0건 → 별건 이연"으로 분류했는데 그 분류가 틀렸다. 빈도 0 은 위험 0 이 아니라 아직 안 밟았다는 뜻이고, 몇 분 만에 밟혔다.

## 2. 🚩 v0.1 이 틀린 이유 (L2 blocker 3건)

v0.1 은 우회 **형태를 열거**했다 — `-c clean.requireForce=…` 와 `git config … clean.requireForce`. 셋 다 뚫렸다(패치본 실측):

| L2 id | 우회 | v0.1 |
|---|---|---|
| `c13e1f3d` | `git -c "clean.requireForce=false" clean -d` — **따옴표 한 쌍** | T1 ⛔ |
| `5a11e396` | `GIT_CONFIG_COUNT=1 GIT_CONFIG_KEY_0=… git clean -d` — **git 정식 env 주입** | T1 ⛔ |
| `46abd809` | `git clean -id` — **`-i` 는 requireForce 를 건드리지도 않는다** | T1 ⛔ |

총 8형태가 뚫린 채였다.

### 세 번째가 결정적이다 — 위협모델이 틀렸다

`git clean -i`(대화형)는 `-f` 없이도, `clean.requireForce` 를 건드리지도 않고 삭제한다. 즉 v0.1 의 "두 갈래(인라인/영속)" 프레이밍 자체가 잘못됐다.

**그 증거는 내가 v0.1 spec 에 직접 인용한 git 에러문에 이미 있었다**:

```
clean.requireForce defaults to true and neither -i, -n, nor -f given; refusing to clean
```

git 이 실행을 허용하는 조건을 스스로 말하고 있다 — **`-i` 또는 `-n` 또는 `-f`**. 인용해 놓고 `-i` 를 못 봤다.

## 3. 설계 — 열거를 버리고(v0.2), 면제도 버린다(v0.4)

git 이 허용하는 세 조건 중 **안전한 것은 `-n`(드라이런) 하나뿐**이다. 그러면 규칙은 이렇게 된다:

> **`git clean` 은 드라이런이 아니면 전부 게이트한다.**

```
[변경 전] git … clean … (-f | --force)          ← 실행 조건 하나만 열거
[변경 후] git … clean  (?! … -n | --dry-run … ) ← 안전 조건만 면제
```

등급 분리는 [대안 C](./2026-09-07-git-clean-t2-separation-spec.md) 를 그대로 유지한다:

| 형태 | 등급 (v0.2) |
|---|---|
| 평문 `git clean …` | **T2** (`git-clean`) |
| 옵션 접두가 하나라도 있는 형태 | **DENY** (`git-destructive`) |
| 드라이런 `-n`·`--dry-run` 및 축약 | 자유 ← **v0.4 에서 폐기** |

### 이 반전이 한 번에 닫는 것

열거가 필요 없다 — **아래가 전부 "드라이런이 아닌 `git clean`"** 이기 때문이다:

- `-f` 계열 · `-i`/`--interactive` · 따옴표 변형 · env 정식 주입 · 설정 해제
- **영속 설정(`git config clean.requireForce false`) 뒤의 `git clean -d`**

마지막이 중요하다. v0.1 은 이 경로를 *"명령 텍스트에 흔적이 없어 원리적으로 탐지 불가"* 라고 단정했는데 — **틀렸다.** 설정을 보려 했기 때문에 그렇게 보였을 뿐, **clean 호출 자체를 보면 잡힌다.**

그래서 v0.2 는 v0.1 의 config 차단(B 갈래)을 **버린다.** 안전 이득이 없어졌고, DENY 층은 heredoc 을 마스킹하지 않아 *문서에 그 문자열을 쓰는 것까지 하드블록*하는 마찰만 남기 때문이다.

### v0.4 — 면제를 **없앤다**

v0.2~v0.3 은 "드라이런이면 면제"를 두고, 그 면제를 속이는 형태를 조건 ②③④ → ⑤⑥ 으로 **열거**했다. L2 3차에서 양 벤더가 합의했다(`2ffe0693`, blocker):

> 면제 조건 ②~⑥ 은 사실상 **"면제를 속이는 형태의 열거"** 라 §2 가 폐기한 열거식 설계의 재현이다. 2사이클 연속 신규 형태 누출과 `-fde -n` 의 라이브 T2 → 패치 T1 완화 회귀가 실측 확증되어, 잔여 미탐이 §1 실사고와 동일한 **T1 자율 삭제**로 착지한다.

맞는 지적이다. 조건을 하나 더 붙여도 목록의 미완결성은 남고, 그 미완결이 착지하는 곳이 실사고와 같은 자리다.

**그래서 면제를 없앤다.** 규칙은 두 줄로 끝난다:

| 형태 | 등급 |
|---|---|
| 평문 `git clean …` (드라이런 포함 **전부**) | **T2** (`git-clean`) |
| 옵션 접두가 하나라도 있는 형태 (드라이런 포함) | **DENY** (`git-destructive`) |

면제가 없으면 **이 층에서는 "면제를 속이는 형태"라는 공격면이 사라진다.** (L2 `dee1f312`: "공격면 자체가 사라진다"는 과장이다 — alias 은닉·변수 간접 같은 **간접화**는 텍스트 게이트의 인식 밖이라 그대로 남는다. §6 · [따옴표 우회 spec](./2026-09-10-quote-bypass-spec.md) §5) ②~⑥ 이 막던 여섯 형태(`--no-dry-run` 상쇄쌍 · 치환 안의 `-n` · `-e` 값 · 결합형 `e` 값 · `--` 뒤 pathspec)는 이제 조건 없이 전부 잡힌다 — 잡으려고 애쓸 대상이 아니라 **그냥 `git clean`** 이기 때문이다.

### 마찰은 실측했다 — 지키려던 것이 실재하지 않았다

면제를 없애면 드라이런 조회도 승인이 필요하다. 그 마찰이 얼마인가:

```
코퍼스 41,307 고유 명령 · 실행경로 git clean
  드라이런     19건  ← 전부 이 트랙의 검증 프로브 자신 (09-07 · 09-10)
  비드라이런   20건
실개발 작업에서의 드라이런 사용:  0건
```

**면제가 지키던 마찰이 실재하지 않았다.** 19건 전부가 이 게이트를 시험하려고 우리가 만든 명령이다. 게다가 T2 는 **승인이지 하드블록이 아니다** — 필요하면 한 번 승인하고 쓴다.

> **19건 ↔ §4B 강화 건수의 관계** (L2 `97300435` 가 짚은 불일치). 같은 스냅샷(41,440)으로 분해하면
> **19 = 이미 게이트 13 + 등급 상승 6.** 13건은 같은 명령줄의 다른 부분(재귀 삭제·설정 변경 등)으로 **이미 T2+ 였어서** 등급이 변하지 않는다 — 그래서 "강화"로 세어지지 않는다. §4B 의 강화 총계는 여기에 비드라이런 형태가 더해진 값이다. 코퍼스는 **우리가 명령을 실행할 때마다 자란다**(41,307 → 41,443) — 그래서 수치는 **측정 시점과 함께** 적는다.

## 4. 검증

### A. 스모크 41건 PASS ✅

v0.1 이 뚫렸던 8형태 + v0.3 까지 면제를 속이던 11형태 + 드라이런 8형태 — **전부 게이트**. 기존 형태(평문·경로인자·결합플래그·체인·`bash -c`·경로형 롱옵션 접두) 등급 유지. 무관 명령(`status`·`log`·`config --get`) 불변.

### B. 고정 코퍼스 전수 — 41,443 고유 명령 (2026-09-11 재측정)

```
강화 · 미탐 해소(실제 실행)   9   ← 전부 이 트랙의 프로브 명령
강화 · 오탐 재발(텍스트 언급)  2 ⚠️ ← 아래
완화                         0 ✅
```

**오탐 재발 2건은 이 문서를 편집한 명령 자신이다.** heredoc 으로 이 spec 을 고치면 본문에 실린 §1 예시 명령이 DENY 층에 그대로 보여 **하드블록**된다(마스킹은 T2 층에만 걸린다 — 층이 다르다). 즉 **v0.4 를 적용하면 이 spec 을 Bash heredoc 으로는 못 고친다.** 회피는 Write 도구로 파일을 쓰는 것이고 이 트랙은 실제로 그렇게 하고 있다. §6 에 마찰로 올린다.

9건 중 1건은 `git -C <경로> clean -n`(드라이런)이 **T1 → DENY** 로 오른 것이다 — 접두형은 드라이런이어도 하드블록이다(§6).

측정 과정에서 **세 번** 되돌아갔다. `git clean --dry-ru` 는 축약 면제를 넣기 전 1건 잡혔고(→ 면제 추가), `git clean -fd -e -n` 은 조건 ④를 넣기 전 완화 1건(→ 조건 추가), 그리고 v0.3 재측정에서 **완화 2건**이 다시 잡혀 조건 ⑤⑥ 이 나왔다(→ §3 인용문). 세 번 다 코퍼스가 먼저 알려줬다 — 스모크만 돌렸으면 세 번 다 놓쳤다.

### C. 기존 시험군 ✅

`risk-classify` 237 · `gate-destructive` 81 · `policy-classify` 53 — 전부 통과.

### D. 영구 회귀 가드 — 81 → 98건

GATE/FREE 15 + **룰 귀속 2** + **기존 드라이런 FREE 2건을 GATE 로 반전**(면제 폐기로 계약이 바뀌었다). 룰 귀속을 넣는 이유는 GATE 축(DENY/T3/T2 아무거나)이 이 설계의 계약인 *"평문=T2 / 접두형=DENY"* 를 구분하지 못하기 때문이다(L2 `6683b216`). 정책과 **한 트랜잭션**으로 쓴다. v0.4 부터 가드 패치본을 **샌드박스에서 먼저 실행해 검증**한다 — 이전에는 가드를 쓰기만 하고 그 패치본으로 돌려보지 않았다. 건수도 세지 않고 **센다**(v0.2.1 의 `81→95` 는 이미 낡아 있었다).

### 3차 (v0.2.1 재측정 — L2 아닌 자체 실측)

L2 2차 지적을 반영한 v0.2.1 을 **적용 직전에 코퍼스 재측정**했더니 완화 2건이 잡혔다. 둘 다 하네스 프로브 명령이라 무해해 보였지만, 그 프로브가 담고 있던 형태를 단독으로 분류해 보니 면제가 뚫려 있었다. 격리 repo 실동작으로 확증:

| 형태 | 패치본(v0.2.1) | 격리 repo 실동작 | 조치 |
|---|---|---|---|
| `git clean -fd -- -n .` | T1 ⛔ | **작업물 전부 삭제** | 조건 ⑤ |
| `git clean -fd -- src -n` | T1 ⛔ | **해당 경로 삭제** | 조건 ⑤ |
| `git clean -fde -n` | T1 ⛔ (라이브는 T2 — **완화 회귀**) | **전부 삭제** | 조건 ⑥ |
| `git clean -fdx -- -n` | T1 | 변화 없음(매칭 경로 없음) | 조건 ⑤ 로 함께 게이트 |
| `git clean -xe -n` | T1 | git 이 거부(`-f` 없음) | 조건 ⑥ 로 함께 게이트 |

`-fde -n` 은 **라이브보다 약해지는** 유일한 형태였다 — 강화 패치가 특정 형태에서 완화로 뒤집히는 경우이며, GATE 축 스모크로는 잡히지 않고 **완화 측정만이 잡는다**.

## 7. 적용

```bash
node ~/p1c/candidates/clean-requireforce/apply.js --check    # 스모크 41 + 시험군 + 가드(패치본 실행까지) 미리보기
node ~/p1c/candidates/clean-requireforce/apply.js --apply    # 정책+시험 원자적, 이어서 Windows 동기
node ~/.ai-bootstrap/gate-destructive.test.js                # 98/98 기대
```

롤백 `apply.js --rollback` — 적용 당시 해시와 대조해 **다른 트랙의 편집이 있으면 거부**하고(`--force` 로만 강행), 통과 시 정책·시험 복원 후 Windows 동기까지 수행한다.

**원자성의 실제 범위** (L2 `56f267e1`): 원자적인 것은 **정책+시험 두 파일**뿐이다. Windows 동기는 그다음 단계이고, 실패하면 경고를 남기며 비정상 종료한다 — 그 사이 Windows 게이트는 **구정책(약한 규칙)** 이다. 동시 적용 잠금은 없다. 부분 실패 시 `maia-deploy.js --check` 로 드리프트를 확인하고 수동 동기해야 한다.

⚠️ 이 명령들은 게이트상 **T1 이라 막히지 않는다.** 지금 이 변경을 실제로 통제하는 것은 게이트가 아니라 **"대표 판정 대기"라는 상태 하나**다(§6 마지막 항목).
